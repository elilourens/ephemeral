# ephemeral — Project Plan

*A self-hostable Discord, with Snapchat-style disappearing messages.*

Last updated: 2026-07-18

---

## 1. What it is

A self-hosted, containerized chat platform. Text channels, voice/video calls,
screen sharing, and file uploads — like Discord — but **everything is ephemeral**:
each message auto-deletes on a **7-day sliding window** (it disappears exactly 7
days after it was posted). Users can **save** individual messages, which exempts
them from deletion. Two roles only: **admin** and **member**. The whole thing runs
from a single `docker-compose up`.

**Design north star:** be aggressively boring and centralized. A large fraction of
the complexity in Matrix, Revolt, and Spacebar exists to solve federation and
multi-node scaling — problems a single self-hosted instance does not have. We
delete that complexity on purpose. (See §11–12.)

---

## 2. Stack (locked)

| Concern | Choice | Notes |
|---|---|---|
| **Backend** | **Java + Spring Boot** | REST + WebSocket + JDBC/JPA + `@Scheduled` in one framework. |
| **Database** | **PostgreSQL 18 + pgvector** | pgvector is an extension on the same container — dormant until we build semantic search over *saved* messages. |
| **Voice / video / screen share** | **LiveKit** (self-hosted SFU) | Apache-2.0. Official Kotlin server SDK (callable from Java) mints access tokens; browser uses the JS client SDK. |
| **Real-time text / presence / typing** | **Native WebSocket** (Spring), in-process `EventEmitter`-style fan-out | Single node → no Redis, no message bus. |
| **File storage** | **Local volume** (default) or **MinIO** (S3-compatible, optional) | Files' lifecycle is bound to their message. |
| **Frontend** | **Plain HTML + CSS + vanilla JS, no build step** | Spring serves static files; browser talks WebSocket + LiveKit JS SDK. |
| **Message IDs** | **UUIDv7**, generated by Postgres (`DEFAULT uuidv7()`) | Time-ordered PK = sort key + pagination cursor + age source in one column. |
| **Packaging** | `docker-compose`: `app`, `postgres`, `livekit` (+ optional `minio`) | No Redis, no RabbitMQ, no Mongo. |

**The one tradeoff we accept:** the JVM idles heavier than Node/Go (~300–500 MB vs
~50–100 MB). Fine for a self-hosted box. If RAM ever matters: Spring Boot + GraalVM
native image, or a lighter framework (Javalin/Quarkus).

## 3. Architecture

```
Browser (plain HTML/JS)
 ├── HTTPS  → app: static files, REST API (login, servers, channels, messages, uploads)
 ├── WSS    → app: real-time text, presence, typing, "message expired" events
 └── WebRTC → livekit: audio, video, screen share  (app only issues a signed join token)

app (Spring Boot) ──JDBC──► postgres (+ pgvector)   users, servers, channels, messages, attachments, saves
app               ──fs/S3─► /data volume | minio     uploaded files
```

The **app is the sole authority**: it owns auth, all data, and issues short-lived
LiveKit tokens. **LiveKit only moves media bytes** and never touches the database.
Three long-running containers; that's the whole system.

## 4. Core feature: the ephemeral engine

This is the product. It must be built so that **deletion is a hard invariant** —
expired content is physically gone, not merely hidden. (Matrix's retention only
*hides* messages while leaving them in the DB, and never deletes the attached
files. We do the opposite of that on every point — see §11.)

**Mechanism**

- Every `messages` row has a **UUIDv7** primary key. The first 48 bits are the
  creation timestamp, so `created_at` is *derived from the id* — no separate column.
- A Spring **`@Scheduled`** job runs frequently (e.g. every 15–60 min) and deletes
  expired, unsaved messages:

  ```sql
  -- :boundary = the minimum UUIDv7 for (now() - 7 days), computed in the app
  DELETE FROM messages
  WHERE id < :boundary          -- hits the primary-key index; no table scan
    AND saved = false           -- the "saved messages don't delete" exemption
  -- batched (e.g. LIMIT 3000 per pass) to avoid long locks / bloat
  ```

  Deleting by PK range keeps it index-only and cheap. `uuid_extract_timestamp(id)`
  (native in PG18) is available as the simple/correct fallback if we skip the
  boundary trick early on.

**Save = exemption.** Saving sets the row out of the delete's reach; a saved
message simply stops matching the query and lives forever. Semantics (default):
**per-user save** — a message survives as long as *any* user has saved it.

- `saves(user_id, message_id)` records who saved what (drives each user's "Saved" view).
- `messages.saved boolean` is denormalized (true while ≥1 save exists) so the delete
  stays index-friendly. Maintained on save/unsave.
- *Alternative to revisit later:* a private per-user **copy** so a saver keeps the
  content even after the channel message would have expired. More storage, more
  code — deferred.

**Media dies with the message.** Attachments are child rows with
`ON DELETE CASCADE`. Because a cascade removes the *rows* but not the *blobs*, the
delete job must: (1) collect storage keys of attachments about to expire, (2) delete
the messages (cascade clears attachment rows), (3) unlink those blobs from disk/MinIO.
A MinIO/object-store lifecycle rule is a good backstop.

**Scale-up path (only if volume demands it):** day-partition `messages` and `DROP`
old partitions for O(1), bloat-free purges. Caveat: a saved row would block a
partition drop, so at that point **saving moves the row into a separate
non-expiring `saved_messages` table** instead of flipping a flag. Not needed for MVP.

## 5. Data model (sketch — Postgres 18)

```sql
users        (id uuid pk default uuidv7(), username text unique, password_hash text,
              display_name text, avatar_media_id uuid null)

servers      (id uuid pk default uuidv7(), name text, icon_media_id uuid null,
              owner_id uuid references users)

channels     (id uuid pk default uuidv7(), server_id uuid references servers,
              name text, type text check (type in ('text','voice')), position int)

memberships  (server_id uuid references servers, user_id uuid references users,
              role text check (role in ('admin','member')) default 'member',
              primary key (server_id, user_id))

messages     (id uuid pk default uuidv7(),            -- id encodes created_at
              channel_id uuid references channels,
              author_id uuid references users,
              content text, edited_at timestamptz null,
              saved boolean default false)            -- denormalized exemption flag

attachments  (id uuid pk default uuidv7(),
              message_id uuid references messages on delete cascade,
              filename text, content_type text, size_bytes bigint, storage_key text)

saves        (user_id uuid references users, message_id uuid references messages on delete cascade,
              primary key (user_id, message_id))

-- Future (pgvector, saved messages only):
-- saved_embeddings (message_id uuid pk, embedding vector(N))
```

**Access patterns**
- Channel history: **keyset pagination**, never OFFSET —
  `WHERE channel_id = ? AND id < :cursor ORDER BY id DESC LIMIT n`
  (stable even as old rows delete underneath; OFFSET drifts and is slow).
- "Saved" view: `saves` joined to `messages` for the current user.

## 6. Voice / video / screen share (LiveKit)

One LiveKit **room per voice channel**. The app never proxies media; it only
authorizes.

**Join flow (the whole thing):**
1. User clicks "Join voice."
2. App checks membership + role for that channel's server.
3. App mints a **short-lived JWT** with the Kotlin server SDK
   (`AccessToken` → `RoomJoin` + `RoomName` grants → `setTtl` → `.toJwt()`),
   mapping role → grants:
   - **admin** → `roomAdmin` + `canPublish` + `canSubscribe`
   - **member** → `canPublish` + `canSubscribe`
4. Browser connects directly to LiveKit with the token.
5. **Screen share** = publishing a track with `source: screenshare`. No extra service.

**Security:** the LiveKit API key/secret live **only** in the app (env vars); tokens
are always minted server-side and short-lived.

**Deployment gotcha (the #1 self-host failure):** open LiveKit's public **UDP port
range**, set `use_external_ip: true`, and enable the built-in **TURN** (3478/5349)
for clients behind strict NAT; TCP fallback on 7881, signaling WS on 7880.

## 7. Auth & roles

- **Auth:** username + password → session cookie or JWT. Passwords hashed (bcrypt/argon2).
- **Roles:** exactly two, **per server**, on the `memberships` row.
  - **admin:** create/delete channels, kick members, promote/demote, (future) set server options.
  - **member:** read/post/save messages, join voice.
- No RBAC engine, no permission bitmasks — a single `role` column checked in a
  Spring filter/interceptor.

---

## 8. Files

- Upload is **decoupled from send**: `POST` file → returns an opaque id → the message
  references it (the Matrix `mxc://` / Revolt "Autumn" pattern).
- **Strip EXIF** on image upload.
- Storage is pluggable: **local volume** by default, **MinIO** via config for S3 semantics.
- Lifecycle is bound to the message (§4): blobs are unlinked when their message expires.

## 9. Frontend

- **No framework, no build.** Static `index.html` + CSS + ES-module JS, served by Spring.
- **WebSocket** for live text/presence/typing; **`fetch`** for REST actions.
- **LiveKit browser SDK** loaded via `<script>` (vendored locally, not a CDN, so the
  app stays fully self-contained/offline-capable).
- Native `getUserMedia` / `getDisplayMedia` are handled through the LiveKit SDK.

Each phase is independently demoable.

2. **Ephemeral text** *(the heart — build first)* — WebSocket messaging, UUIDv7

5. **Voice** — LiveKit token endpoint + "Join voice" button.
6. **Video + screen share** — same room, camera + `getDisplayMedia` tracks.
7. **Admin** — kick, delete channel; polish presence/typing.

## 11. Best practices we're adopting (from the research)

Derived from studying Matrix, Revolt/Stoat, Spacebar, Mattermost, and Rocket.Chat.

- **Don't build an SFU — use LiveKit.** Unanimous: Matrix's official stack
  (Element Call) runs on LiveKit, and Revolt *ripped out* their own mediasoup SFU
  ("an unstable mess") for LiveKit. Nobody who could avoid it built their own.
- **Postgres is the validated core.** Both Spacebar and Mattermost dropped their
  other databases to consolidate on Postgres-only. (This is also why the vector idea
  lives as `pgvector` on the same box, not a separate DB.)
- **Retention = a scheduled delete job with a "saved/pinned" exemption**, never a
  DB TTL (Postgres has none). Directly mirrors Mattermost's `PreservePinnedPosts`
  and Rocket.Chat's `excludePinned`.
- **Invert Matrix's retention mistakes:** physical deletion (not "hide"), no
  category exemptions, no "always keep ≥1 message," and **cascade the delete to
  media** (Matrix leaves files orphaned forever).
- **Time-ordered message IDs (UUIDv7):** sort key, keyset cursor, and age-from-id in
  one column; dodges the JS 53-bit-integer problem that forces Discord/Spacebar to
  ship IDs as strings.
- **Keyset pagination, never OFFSET** — O(1) per page and stable while rows expire.
- **One process + in-process fan-out.** Revolt runs 7+ microservices, Spacebar 4
  bundles glued by a message bus — all to fan events across *nodes*. Single node
  needs none of it. (Postgres `LISTEN/NOTIFY` is the escape hatch if a 2nd node ever appears.)

## 12. Deliberately out of scope

Everything whose only justification is decentralization or multi-node scale:

- **Federation** — server-to-server replication, DAG/event graph, state resolution,
  room versions. Replaced by one ordered table.
- **End-to-end encryption** — beyond the implementation cost, E2EE *fights* our
  requirements: it breaks server-side search, moderation, and reliable deletion (the
  last is fatal for an auto-delete product). TLS in transit + server-side authz is
  the correct trade-off for a trusted, self-hosted app.
- **Microservices / message bus (Redis, RabbitMQ, NATS), MongoDB.**
- **Discord API compatibility**, snowflake IDs, permission bitfields, granular
  per-channel retention policies, embed/GIF/push side-services.

## 14. Build notes (as-built)

The MVP is implemented and tested. A few pragmatic deviations from the design
above, driven by the build environment:

- **UUIDv7 generated in Java** (the `uuid-creator` lib), not by Postgres 18's
  native `uuidv7()`. This makes the app portable to any Postgres 13+ (the compose
  stack uses the `pgvector/pgvector:pg16` image) and keeps id generation in one
  place. `util/Ids.java` also computes the retention boundary and extracts the
  creation instant from an id.
- **LiveKit token minted directly** with `jjwt` (`voice/LiveKitTokenService`)
  rather than pulling the Kotlin server SDK — a LiveKit access token is just an
  HS256 JWT with a `video` grant claim, so this keeps dependencies light. Verified
  by decoding the token in the E2E tests (admin → `roomAdmin`, member → not).
- **Dev/test Postgres via `zonky` embedded-postgres** — real Postgres, no Docker,
  no install. The `dev` profile boots it automatically (`config/DevDatabaseInitializer`);
  the E2E tests start their own. In containers this is inert — compose provides PG.
- **Data access is plain SQL** via `NamedParameterJdbcTemplate` (not JPA), matching
  the plan's guidance to keep full control over keyset pagination and the batched
  purge. `pgvector`/Hibernate can be added later for saved-message search.
- **Retention purge is a Spring `@Scheduled`-style task** (`config/SchedulingConfig`
  + `message/RetentionService`) — no `pg_cron` needed; it runs in-process.
- **Frontend vendors the LiveKit browser SDK** locally (`static/vendor/`) so the
  app is fully self-contained with no runtime CDN dependency.
- **Auth** is a lightweight JWT filter (`auth/AuthFilter`) + BCrypt from
  `spring-security-crypto`, not the full Spring Security starter.

## 15. Retention design review — validated against the field

Researched how Discord, Revolt/Stoat, Spacebar, Matrix, Mattermost, and DB-native
TTLs actually delete ephemeral messages + files, and **empirically benchmarked the
alternatives via Docker**.

**Verdict: our design is correct and idiomatic.** Hard-delete + an in-app scheduled
sweep + a `saved`-exempt carve-out is exactly what Revolt/Stoat (a 60s `crond`) and
Mattermost (a nightly batched delete of rows *and* files) ship. The UUIDv7 primary-key
range-delete mirrors how Discord derives time buckets from Snowflakes. We also avoid
Matrix's known quirks (it *hides* rather than deletes, always keeps ≥1 message, and
decouples media retention from message retention).

**Empirical comparison (Postgres/Mongo containers, 800k rows, purge everything >7 days):**

| Approach | Purge time | Disk reclaimed | `saved`-exempt? |
|---|---|---|---|
| **Ours** — scheduled `DELETE WHERE id < boundary AND saved=false` | 89 ms | no — table stays 105 MB until VACUUM | ✅ SQL predicate |
| **Postgres day-partition + `DROP`** | **3 ms** | ✅ instant (partition files unlinked) | needs saved rows in a separate table |
| **MongoDB TTL index** | ~63 s sweep, zero app code | ✅ | ❌ single date field (`null` to exempt) |

So the concrete "better way" **at scale** is daily partitioning + `DROP PARTITION`
(O(1), no VACUUM/bloat — the Postgres docs endorse it for rolling windows), with saved
rows moved to a separate non-expiring table. At single-node MVP volume our batched
DELETE is precisely what real products use, so partitioning is the documented scale-up
path, not an MVP need. (MongoDB TTL is out because it *cannot express* our
`saved`-exempt rule — a point in favor of staying relational.)

**Gap found and fixed.** The field's most common failure here is *orphaned files*
(Spacebar's bulk-delete bypasses its own file hook; Rocket.Chat/Matrix leave blobs on
disk). Our inline unlink is best-effort, so a failed unlink could orphan a blob forever.
**Added a reconciliation sweep** — `RetentionService.reconcileOrphanBlobs` (scheduled) —
which removes on-disk blobs that have no attachment row and are older than a grace window
(default 1h, sparing freshly-uploaded-but-not-yet-bound files). Covered by
`orphanBlobsAreReconciled`.

**Documented scale-up backlog (not needed at MVP):** day-partitioning + `DROP` with saved
rows carved out; `REINDEX INDEX CONCURRENTLY` for leftmost B-tree bloat; per-batch COMMIT
+ an advisory lock; autovacuum tuning on `messages`.

### Multi-client + retention, validated end-to-end
- **3 isolated browser clients** (Playwright): chat cross-delivered live both ways; all

## 17. Discord parity wave — 10 high-use features

Sourced from Discord UI screenshots; the 10 most-used interactions we were missing, all
built and verified headless (`browser/features-e2e.mjs`, **23/23**):

1. **Markdown** — hand-written tokenizer (escapes first → XSS-safe): `**bold**`, italics,
   `__underline__`, `~~strike~~`, inline+fenced `code`, `> quote`, `||spoiler||` (click to
   reveal), and `<@id>` → mention chip.
2. **Emoji reactions** — `message_reaction` table; pills below the body, `.mine` when yours;
   toggle via `POST /api/messages/{id}/react`; live over `message_updated`; counts aggregate.
3. **Hover toolbar** — React / Reply / Edit / Pin / Save / Delete / More on every row.
4. **Context menus** — generic `openContextMenu()`; right-click a message (Copy Text/Link/ID,
   pin, save, delete), a user (profile, mention, copy id), or a channel (mark read, copy link).
5. **@mention autocomplete** — `@`-triggered member popup; inserts a chip; `convertMentions()`
   rewrites to `<@id>` on send; server records `message_mention` + bumps `read_state`.
6. **Unread state** — `GET /api/guilds/{id}/read-state` + `POST /api/channels/{id}/ack`; bold
   channel + dot + red mention badge; never-read channels baselined at their tip so only
   *new* activity (or a mention) surfaces; **"New messages" divider** at the boundary.
7. **Emoji picker** — searchable, category-tabbed (~200), from composer + reaction paths.
8. **Jump to present** — floating bar when scrolled up; click scrolls to newest + acks.
9. **Pinned messages** — `messages.pinned/pinned_at`; header pushpin lists pins; pinned rows
   flagged; author/admin only; **excluded from the retention purge**.
10. **Copy link / ID + deep-link** — clipboard copy; `#m/<ch>/<msg>` opens the channel and
    flashes the message; hover-timestamps on grouped rows retained.

**Schema:** `V3__reactions_pins_reads.sql` — `message_reaction`, `messages.pinned/pinned_at`,
`message_mention`, `read_state`. `MessageDto` gains `pinned/reactions/mentions`.

**Two real bugs found and fixed while testing (not just the features):**
- **Cross-channel delivery.** Message events were fanned out only to *channel* subscribers,
  and the client subscribes to one channel at a time — so unread/mentions for channels you
  weren't viewing never arrived. Added **guild-scoped subscription** (`subscribe_guild`,
  `RealtimeService.guildSubs` + a cached channel→guild lookup); `message`/`message_updated`/
  `message_deleted` now broadcast guild-wide (all channels are visible to all members, so no
  leak). Typing stays channel-scoped.
- **`function max(uuid) does not exist`.** The read-state query used `max(mm.id)` — Postgres
  has no `max()` aggregate for `uuid` (though uuid *is* orderable). Replaced with
  `order by id desc limit 1`. The endpoint had been silently 500ing (client fell back to an
  empty snapshot). Now covered by a JUnit test (`readStateReactionsAndPins`).
- **Layout scroll bug.** `.app-shell` grid had `height:100vh` but an implicit `auto` row, so a

## 19. Voice/Video settings + audio DSP, GIFs, link embeds

Researched livekit-client **v2.20.1** APIs and OWASP SSRF / iframe-embed best practices
first (two research passes), then built + tested each piece.

### Voice & Video Settings (a real settings modal — gear in the voice bar and the
user panel)
- **Device pickers** (mic / speaker / camera) via `enumerateDevices` (labels appear
  after the mic grant that also powers the meter) → applied live with
  `room.switchActiveDevice()` / `LocalAudioTrack.restartTrack()`; speaker via
  `setSinkId` on the remote `<audio>` elements.
- **Audio cleaning** toggles: Echo Cancellation, Noise Suppression, **Voice Isolation**
  (Chromium's strongest NS — and livekit v2.20 defaults it *on*, silently overriding
  NS, so we always pass it explicitly), Automatic Gain Control. Applied live by
  `restartTrack(audioCaptureDefaults())` — note restartTrack REPLACES constraints, so
  the full set is always passed.
- **Crispiness**: mono (`channelCount:1` keeps Opus DTX+RED) + `AudioPresets.music`
  (48 kbps), and a **High-Quality Audio** toggle → `musicHighQuality` (96 kbps).
- **Input Volume** (0–200%): a Web-Audio `GainNode` inserted via livekit's
  `LocalAudioTrack.setProcessor()` so it changes what *others* hear, adjustable live.
- **Live input meter**: AnalyserNode on the actual published mic track (or a temp
  capture when not in a call).
- **Configurable screen-share quality**: resolution (720/1080/1440), frame rate
  (15/30/60) and Clarity/Balanced/Motion → `ScreenShareCaptureOptions.contentHint`
  (`text`/`detail`/`motion`) + a single non-simulcast `screenShareEncoding`
  (bitrate scaled by fps). Krisp is Cloud-gated so native constraints are the
  correct self-host path (confirmed).

### GIFs + link embeds (client)
- Message content is scanned for up to 3 bare URLs (never inside code) and embedded:
  image/gif/webp → `<img>`; mp4/webm → `<video>`; mp3/… → `<audio>`; **YouTube** →
  click-to-play facade → `youtube-nocookie.com/embed` iframe (nothing hits Google
  until click); **Vimeo / Spotify / Twitch** → provider iframe whose src is REBUILT
  from an extracted ID (never the raw URL), with a locked-down `sandbox`/`allow`.
- **GIF picker** (composer `GIF` button) backed by Tenor **through the server** so the
  key never reaches the browser; gracefully tells you to set `ephemeral.tenor-key`
  when absent (pasted GIF links embed regardless).

### Rich link embeds (server unfurl — the SSRF-sensitive part)
- `GET /api/unfurl?url=` (authenticated) → `UnfurlService` fetches via
  `SafeUrlFetcher` and parses OG/twitter/`<title>`/theme-color with jsoup, returns a
  card DTO (cached 15 min, positive+negative).
- **`SafeUrlFetcher`** = the OWASP SSRF guard: http/https only, no userinfo, resolves
  every host and rejects if ANY address is loopback/private/link-local/CGNAT/reserved
  or the `169.254.169.254` metadata range (IPv4 + IPv6 incl. v4-mapped/ULA/6to4/NAT64),
  **follows redirects manually re-validating each hop**, caps redirects/size/time, and
  gates on an HTML content-type before reading the body. `ephemeral.allow-private-unfurl`
  (tests only) opens the guard for a loopback fixture.

**New backend:** `unfurl/{SafeUrlFetcher,UnfurlService,UnfurlController}`,
`gif/GifController`, `dto/UnfurlDto`, jsoup dep, `AppProperties.{allowPrivateUnfurl,tenorKey}`.

**Verified — 30/30 JUnit** (adds **7** `SafeUrlFetcherTest` incl. a live-loopback-server
"still blocked" test + every reserved range, and **4** `UnfurlApiTest`), plus browser
suites: `livekit-apply` 12/12 (constraints reach `getSettings()`; `restartTrack` flips
echo/noise/AGC live; gain processor publishes a live track; screen honors resolution +
contentHint), `voice-settings` 15/15, `embeds` 12/12 (real example.com OG card, facade→
iframe, code-block exclusion, XSS-inert), `media-e2e` 12/12 regression (real SFU call
with the new RoomOptions + screenshare quality path), and features/context-menus/
channel-crud/multiclient all green. Server log clean.

## 20. Rail notifications, admin channels, voice state, search, account deletion

Big batch, researched (Discord visuals + Postgres FTS/pgvector) then built + tested.
Schema `V4__admin_channels_settings_search.sql`: `channels.admin_only`, `users.settings`
jsonb, and a STORED `messages.content_tsv` generated column + GIN index.

- **Server-rail notifications** (Discord-style): white pill on a server icon's left edge
  (8px unread / 20px hover / 40px active) + red numbered mention badge bottom-right. Client
  now subscribes to EVERY guild it's in and loads read-state for all of them, so the rail
  updates live for servers you aren't viewing. Muted servers/channels suppress the pill but
  still count mentions. Also: desktop **Notifications** (permission opt-in) + a WebAudio
  **ping** + a `document.title` mention badge on @mentions.
- **Admin-only channels**: `admin_only` flag, a create-modal toggle + a lock glyph on the
  channel row + a context-menu "Make Admin-Only / Make Public". Enforced server-side in
  `requireChannelMember`/`isChannelMember` and hidden from non-admins in `buildGuild` — a
  non-admin can't see, read, post, or search them.
- **Voice state** — a green **speaking ring** on tiles (LiveKit `ActiveSpeakersChanged`);
  self **mute** + **deafen** (deafen mutes everyone for you AND force-mutes your mic);
  screen-share. All three propagate to everyone via a `voice_state` WS message →
  `VoicePresenceService` (now carries muted/deafened/screen per participant) → the sidebar
  voice list (mic-off / headphone-off / red **LIVE** badge) and the call tiles.
- **Message search** (`GET /api/search`): Postgres FTS over `content_tsv` with
  `websearch_to_tsquery`, scoped to the viewer's memberships, admin-only channels never leak;
  `from:`/`in:`/`has:link|image|file` filters + recent/relevant sort; a header search button
  opens a results panel with jump-to-message. (pgvector semantic search intentionally
  deferred — it needs an embedding source; flagged to the user.)
- **Account deletion** (`DELETE /api/users/me`): removes owned servers (cascade) + every
  message the user ever posted anywhere + uploads (blobs too) + memberships/reactions/
  mentions/read-state, then the user. UI requires typing your username to confirm.
- **Settings persistence**: `users.settings` jsonb via `GET/PUT /api/users/me/settings`; the
  client syncs its media prefs + mute lists there, so they survive restarts and follow the
  account (localStorage stays a fast cache; browser-specific device ids fall back to default).
- **UI/UX**: applied Discord's 8px spacing rhythm (group separation, line-height) and — the
  big one — **fixed a `.content` CSS class collision** where the layout pane's
  `display:flex` was blockifying message inline elements (bold/links/inline-code were
  stacking vertically on their own lines). Scoped the layout rule to `#content`; added a
  computed-style regression guard.

scoping + admin-only isolation + `from:`/`has:`, and account-deletion + settings roundtrip),
